# Reproducible OCR UI checks

The browser's engine-selection contract and real OCR accuracy are different
checks. The focused suite below uses an in-memory generated PNG and intercepted
API responses. It needs no private photos, Python backend, OCR models, database,
or provider key. It does **not** measure recognition accuracy or legal correctness.

## Clean-checkout quick check

Use Node.js 22.13 or newer, as required by the root package:

```sh
npm ci --workspace @metrology/web --include-workspace-root
npx playwright install chromium
npm run test:contracts
npm run typecheck --workspace @metrology/web
npm run test:ocr-ui
```

`test:ocr-ui` starts the existing Next.js development server on port 3001 and
stops it afterward. In local development it can reuse an existing server on that
port. Set `TEST_WEB_URL` only to a development/test instance you intend to test;
with that variable set, you must start the web app yourself. API calls are
intercepted, so the suite does not create real inspections.

For managed environments with an already-installed compatible Chromium:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:ocr-ui
```

The default remains Playwright's downloaded Chromium. Record the browser version
when using a system executable; it may differ from Playwright's pinned version.

### Assertions defined by the focused checks

These are assertions implemented in the test files. Their presence and successful
test discovery do not establish that the browser test bodies have passed.

- Shared-client multipart contracts, upload limits, failure messages and aborts.
- Optional reference-photo path validation, including missing files and directories.
- Default Both selection and Tesseract selection persistence across reload.
- All three engine values in the actual multipart browser requests.
- The exact uploaded image bytes and filename remaining unchanged across scans.
- Engine/scan controls disabled while a mocked scan is in flight.
- Rendering a clearly simulated response and retaining the selected image.
- Recovery after a mocked 422 response and retry with another engine.

The generated one-pixel PNG is transport input, not a product label. A mocked
successful response does not prove OCR execution, PDF generation, database
persistence, or production readiness.

## Private reference-photo integration test

`tests/ocr-engine-choice.spec.ts` retains the original strict reference-photo
assertions: each real engine must return `₹ 99.00` with `REVIEW`, and the returned
report must begin with the PDF signature.

The reference coffee-label photo is **not** committed. Previously the test
unconditionally read `work/migration-coffee.jpg`, which does not exist in a clean
checkout and is not generated by `scripts/prepare-test-fixtures.py`. That script
only produces the two synthetic Atta package-side fixtures.

Start the web app and a separately configured local test API with both OCR
runtimes, using [STACK_MIGRATION.md](STACK_MIGRATION.md). Use an isolated
`METROLOGY_DATA_DIR`: real integration scans create inspections and reports.
Point the web app's `METROLOGY_API_URL` or `NEXT_PUBLIC_API_URL` to that same API.
Then supply the known reference photo explicitly:

```sh
OCR_COFFEE_IMAGE=/absolute/path/to/reference-coffee.jpg \
TEST_WEB_URL=http://127.0.0.1:3001 \
TEST_API_URL=http://127.0.0.1:8000 \
npm run test:ocr-reference
```

Relative photo paths resolve from the repository root. If the variable is unset
or blank, Playwright reports the reference-photo test as **skipped**, not passed.
If it is set to a missing, unreadable, or non-file path, test discovery fails with
an actionable message. The optional coffee check in `web-migration.spec.ts` uses
the same validation and no longer silently ignores an invalid configured path.

The path helper checks file accessibility, not image content or ground truth.
Use the actual reference photo and human-reviewed label; do not substitute an
arbitrary image or adjust expectations until a failing OCR result looks green.
Screenshots and timing records go into Playwright's per-test output directory
under ignored `work/playwright-results/`. These timings are diagnostic observations,
not benchmarks.

## Wider verification and limitations

`npm run test:web` still includes backend-dependent, mobile-server-dependent, and
other fixture-dependent integration tests. Passing the focused suite is not a
pass of that entire suite. See the existing migration, barcode, and voice guides
for those dependencies. Live providers and physical-device behavior are outside
this focused suite.

`npm run build` checks the Next.js production build; `npm run typecheck` checks
all installed workspaces. The focused web-only installation above does not
install or verify the Expo mobile workspace.
